# Chartered Accountant Profile & Firm Website

A static website for an Indian Chartered Accountant and their practice. It uses plain HTML, CSS and JavaScript (ES modules), with no backend, database, framework or build step.

All content lives in one file, [`src/data/site-data.js`](src/data/site-data.js). Edit that file and every page updates.

> ⚠ **Everything currently in `site-data.js` is sample content.** "Aarav Mehta", "Artha & Co.", the phone numbers, emails and address are fictitious. Work through [CONTENT-REVIEW.md](CONTENT-REVIEW.md) with the CA before going live.

---

## 1. Run it locally

ES modules don't load from `file://`, so serve the folder over HTTP:

```bash
cd ca-website
python3 -m http.server 8080        # or: npx serve .
```

Open <http://localhost:8080/>. The site works at `/` locally even while `basePath` is `/ca/`, because all internal links and assets are relative. `basePath` only affects canonical URLs, social tags, the sitemap and the 404 page.

To preview exactly as it will run under `/ca/`:

```bash
mkdir -p /tmp/preview && ln -s "$PWD" /tmp/preview/ca
cd /tmp/preview && python3 -m http.server 8080      # → http://localhost:8080/ca/
```

## 3. Updating content (no code changes)

Open `src/data/site-data.js` in any text editor. Each section has comments. Keep the quotes and the commas at line ends.

| To change… | Edit |
|---|---|
| CA name, photo, bio, qualifications | `profile` |
| Firm name, logo, mission, values, team | `firm` |
| Phone, WhatsApp, email, address, hours, map | `contact` |
| LinkedIn / social links | `social`, `profile.links` |
| Services | `services` (and `categories`) |
| Who you serve, how you work, commitments | `clientSegments`, `process`, `commitments` |
| FAQs | `faqs` |
| Section headings and button text | `pages` |
| Page titles and descriptions for Google | `seo` |
| Privacy policy, disclaimer | `privacy`, `disclaimer` |
| Footer text | `footer` |

**Example: change the WhatsApp number.** Set `contact.whatsapp: "+91 99999 88888"`, save, then deploy. Every WhatsApp button, the floating button, the footer and the contact page all update. Use `""` to remove WhatsApp everywhere.

**Tokens.** Write `{firm}`, `{firmLegal}`, `{ca}`, `{caName}`, `{designation}`, `{city}`, `{email}`, `{phone}`, `{website}` or `{year}` in any text and they're filled in automatically. Names are typed only once.

**Images.** Put files in `assets/images/` and reference them as `"assets/images/photo.jpg"`. Don't start the path with `/`. For the portrait, use about 800×1000 px (4:5) JPG or WebP under 200 KB. For the social image (`ogImage`), use 1200×630 PNG or JPG. To change the favicon, replace `assets/icons/favicon.svg`.

After editing, run `node scripts/generate-seo.mjs` (see §7) if Node is installed. On GitHub Pages this happens automatically at deploy time. It's optional, but it refreshes titles, the sitemap and social previews, and it reports configuration mistakes.

### Adding a service

Copy an existing entry in `services`, give it a unique `id` (lowercase, hyphens) and set `category` to one of the `categories` ids:

```js
{
  id: "nri-taxation",
  name: "NRI Taxation",
  category: "taxation",
  icon: "globe",
  order: 5,
  enabled: true,
  featured: false,            // true = also shown on the homepage
  shortDescription: "Returns, TDS refunds and repatriation for non-residents.",
  description: ["Paragraph one.", "Paragraph two."],
  targetAudience: ["NRIs with Indian income"],
  scope: ["Item", "Item"],
  deliverables: ["Item"],
  cta: { label: "Enquire about NRI taxation" },
},
```

It appears on the services page, in the contact-form dropdown, in the footer category links and at `service.html?id=nri-taxation`, with no other changes. Set `enabled: false` to hide a service everywhere. `internal-audit` in the sample data shows how.

**Available icons:** `receipt calculator percent file-text shield-check clipboard-check book-open briefcase building landmark chart compass scale users user rocket store factory heart globe lock eye target layers award graduation message search info phone whatsapp mail map-pin navigation calendar clock linkedin home check`

### Draft mode and verification flags

`website.draftMode: true` shows a "sample content" ribbon. **The site cannot be deployed to GitHub Pages while draft mode is on** (see §4). It also shows professional claims marked `verified: false` (qualifications, career entries, membership, practice year, credentials) with an **Unverified sample** tag.

When `draftMode` is `false`, **anything not marked `verified: true` is hidden.** Testimonials and achievements are also switched off (`enabled: false`) by default. Testimonials additionally need `consentOnFile: true` per item.

## 4. Deploying with GitHub Pages (recommended)

The workflow in [`.github/workflows/site.yml`](.github/workflows/site.yml) tests the site and publishes it. Nothing is built by hand.

### Getting `/ca/` on your domain

GitHub Pages serves a repository named **`ca`** at `https://<your-user-site>/ca/`. If your personal site is a GitHub Pages user site with a custom domain (e.g. `yourdomain.com`), a repository named `ca` is automatically available at **`https://yourdomain.com/ca/`**.

| Personal site | Repository name | Site address | `siteUrl` | `basePath` |
|---|---|---|---|---|
| GitHub Pages with custom domain `yourdomain.com` | `ca` | `https://yourdomain.com/ca/` | `"https://yourdomain.com"` | `"/ca/"` |
| No custom domain | `ca` | `https://username.github.io/ca/` | `"https://username.github.io"` | `"/ca/"` |
| Hosted elsewhere (not GitHub Pages) | n/a | Use Nginx (§5) or a reverse proxy | | |

### One-time setup

1. Push this project to the repository (e.g. `username/ca`).
2. **Settings → Pages → Build and deployment → Source: GitHub Actions.**
3. Set `website.siteUrl` and `website.basePath` as in the table above.

### What runs, and when

| Trigger | Jobs |
|---|---|
| Any push or pull request | **Validate** (syntax, configuration errors) → **Browser tests** (under `/ca/` and `/`) → release check as an *advisory* report |
| Push to `main` or manual run | Validate → Browser tests → **Release gate** (blocking) → **Deploy** |

**The release gate blocks deployment** until the content is ready to go live ([`scripts/check-release.mjs`](scripts/check-release.mjs)):

- `website.draftMode` must be `false`
- no sample or placeholder content in any published section: `[brackets]`, `SAMPLE`, `example.com`, the template's sample names and numbers, LinkedIn links without a profile
- `siteUrl` + `basePath` must equal the GitHub Pages URL for the repository
- the placeholder portrait must be replaced, and every referenced image must exist
- testimonials, if enabled, must have consent and verification
- there must be no configuration errors

Each problem is reported with a link to the exact line in `site-data.js`, plus a summary on the workflow run page. Advisory notes don't block: sample logo or favicon, form not connected, unverified items that will be hidden.

You can run the same check locally:

```bash
node scripts/check-release.mjs              # what the gate will say
EXPECTED_BASE_URL=https://yourdomain.com/ca node scripts/check-release.mjs
```

While the CA is still reviewing content, keep working on a branch or in pull requests. Those runs show the advisory report but never deploy. Merge to `main` once the report is clean.

At deploy time the workflow regenerates SEO tags, `sitemap.xml`, `robots.txt` and the 404 page from `site-data.js`. It then publishes only the public files (`*.html`, `src/`, `assets/`, sitemap, robots), so you don't need to commit generated files by hand.

**Domain-root `robots.txt`:** crawlers only read it from the domain root. Add `Sitemap: https://yourdomain.com/ca/sitemap.xml` to the robots.txt of your personal site's repository.

**Recommended:** in Settings → Branches, add a protection rule for `main` that requires the *Validate configuration* and *Browser tests* checks to pass. This catches broken edits before they reach `main`.

## 5. Deploying under `/ca/` with Nginx (alternative)

1. In `site-data.js` set:
   ```js
   siteUrl: "https://yourdomain.com",
   basePath: "/ca/",
   draftMode: false,          // after content review
   ```
2. Run `node scripts/generate-seo.mjs`. This writes canonical URLs, the sitemap and the 404 page's `<base href="/ca/">`.
3. Upload the project so that `index.html` sits at `<web-root>/ca/index.html`. Leave out `node_modules/`, `tests/`, `scripts/` and `deploy/` (the Nginx example also blocks them).
4. Add the blocks from [`deploy/nginx-subpath.conf`](deploy/nginx-subpath.conf) to your existing `server { }` and reload: `sudo nginx -t && sudo systemctl reload nginx`.
5. Add `Sitemap: https://yourdomain.com/ca/sitemap.xml` to the **domain-root** `robots.txt`. Crawlers ignore `/ca/robots.txt`.

The `/ca` → `/ca/` redirect matters: the pages use relative paths, which need the trailing slash.

`/ca/` is configured in **one place** (`website.basePath`). Nothing else in the code mentions it. The generator copies it into `404.html`, `sitemap.xml` and `robots.txt`.

## 6. Deploying at the root (`/`)

On GitHub Pages, use a repository named `username.github.io`, or set a custom domain on the repository. Set `basePath: "/"` and the matching `siteUrl`; the workflow does the rest.

With Nginx, set `basePath: "/"` and `siteUrl` to the (sub)domain, run `node scripts/generate-seo.mjs`, upload to the web root and use [`deploy/nginx-root.conf`](deploy/nginx-root.conf).

Other static hosts work as well. For Apache, add `ErrorDocument 404 /ca/404.html`. GitHub Pages and Netlify pick up `404.html` automatically. Make sure `.js` is served as JavaScript.

## 7. SEO

- Each page's title, description, canonical URL and Open Graph tags come from `seo` in `site-data.js`. They're set in the browser and also written into the HTML by `scripts/generate-seo.mjs` for link previews and crawlers that don't run JavaScript.
- Each service page uses the service's name and short description.
- `sitemap.xml` lists all pages and every enabled service.
- Schema.org JSON-LD (`AccountingService`) is available but **off** (`seo.structuredData.enabled`). Turn it on once details are final and approved.

```bash
node scripts/generate-seo.mjs        # Node 18+, no packages required
```

## 8. Enquiry form

The site is static, so form submissions need a third-party form service.

1. Create a form at a provider such as Formspree, Getform, Basin or Web3Forms.
2. Set `enquiryForm.endpoint` to the HTTPS endpoint URL. Also set `providerName` and `providerPrivacyUrl`; the privacy policy then names the provider automatically.
3. Use `format: "json"` (Formspree, Getform) or `"form"`, as the provider requires.
4. Enable the provider's spam filtering. The form includes a hidden honeypot field (`honeypotField`, default `_gotcha`).

**Never put secret API keys in `site-data.js`.** It is public.

With **no endpoint**, the submit button is disabled and a notice explains that online submission isn't set up. Visitors can still use **Send via WhatsApp** or **Send via email**, which open their own app with the message pre-filled. The site only ever shows "sent" after the provider returns a successful response.

## 9. Integrations that need external setup

| Integration | Where | Notes |
|---|---|---|
| Form service | `enquiryForm.endpoint` | Required for the online form; WhatsApp/email work without it |
| Google Maps link | `contact.mapsUrl` | Search or share link for the office |
| Google Maps embed | `contact.mapsEmbedUrl` | Maps → Share → Embed → copy the `src` URL; loads only after the visitor clicks "Show map" |
| Appointment booking | `contact.appointmentUrl` | Calendly, Google Calendar booking page, etc. |
| WhatsApp | `contact.whatsapp` | Uses `wa.me` links; no API account needed |
| LinkedIn / social | `social`, `profile.links` | Plain links |
| GitHub Pages | repository Settings → Pages | Source: GitHub Actions (§4) |
| Domain-root robots.txt | your main site | Add the `Sitemap:` line (§4) |

There are no analytics, trackers or third-party scripts. Fonts are self-hosted.

## 10. Testing

These run automatically in CI (§4). To run them locally:

```bash
npm ci && npx playwright install chromium
npm test                       # browser tests
npm run check:release          # go-live readiness
```

The tests read `site-data.js`, so they keep passing after the sample content is replaced. `tests/acceptance.mjs` serves the site under the configured `basePath`, `/ca/` and `/`, and checks the following:

- every page loads without errors and with no horizontal overflow
- all internal links resolve and stay inside the base path
- navigation and the mobile menu work
- contact links match the config
- disabled services are hidden
- category filtering works
- a deep URL gets the styled 404 page with all assets loading
- the form never reports false success, and succeeds only on an OK response
- the entry disclaimer works
- adding a service or changing the phone number in `site-data.js` updates every page with no other edits
- `draftMode: false` hides unverified claims

## 11. Accessibility and performance

- Semantic landmarks, a single `h1` per page, a skip link, visible focus styles, labelled form fields with inline errors, and `aria-current` on navigation. The FAQ uses `<details>` and the entry dialog uses `<dialog>`.
- Animations respect `prefers-reduced-motion`.
- Fonts are self-hosted woff2 (~125 KB in total; the two main files are preloaded) with `font-display: swap`. Images below the fold are lazy-loaded. There are no dependencies to download.
- All configurable text is inserted as text, never as HTML, so content edits can't break or inject markup.
